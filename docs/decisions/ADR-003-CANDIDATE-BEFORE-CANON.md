# ADR-003: 候选先于正典 (Candidate Before Canon)

## 状态

已接受 (2026-07-24)

## 背景

灵笔当前的 AI 续写流程：
1. 用户请求续写
2. AI 生成文本
3. 文本直接追加到正文
4. 保存

问题：
- AI 输出未经审核直接进入正文
- AI 可能修改角色设定（如让已死角色复活）
- 没有"候选"概念，无法比较多个方案
- 用户约束："AI 能承担大量执行工作，但不允许 AI 未经确认修改正式正典"

OpenWrite 的解决方案：写章使用事务，正文/真相文件/记忆作为提交单元，失败回滚。

## 决策

**AI 的所有输出默认都是候选（Candidate），必须经过作者采纳才能成为正式内容。**

规则：
1. AI 输出 → 写入 `candidates/` 目录
2. 审稿 Agent 评估候选（可选但推荐）
3. 作者查看候选（diff 视图）
4. 作者采纳 → 候选移入正文/正典
5. 作者拒绝 → 候选归档
6. 采纳后 → 触发结算（更新运行态）

**采纳与结算分开：**
- 采纳 = 作者确认"这个内容成为正式正文"
- 结算 = 系统从已采纳正文中提取事实，更新运行态

**AI 不能直接修改正典：**
- AI 可以建议修改正典（生成候选正典条目）
- 但必须经过作者采纳才能写入 `canon/`

## 理由

1. 用户明确要求"AI 未经确认不得修改正式正典"
2. OpenWrite 验证了事务回滚对长篇写作的保护价值
3. 候选机制允许比较多个 AI 方案
4. 分离采纳和结算避免"采纳了但状态没更新"或"状态更新了但作者没确认"
5. 防止 AI 在 50 章后"跑偏"直接污染正文

## 后果

- 正面：作者始终拥有最终控制权
- 正面：可以比较多个候选方案
- 正面：AI 错误不会直接污染正文
- 正面：结算保证运行态与正文一致
- 负面：增加了一步操作（采纳）
- 负面：需要候选区存储管理
- 缓解：对于简单续写，可以提供"快速采纳"一键操作

## 来源

- OpenWrite：事务回滚 + 写前快照
- 用户约束："不允许 AI 未经确认修改正式正典"
- 圆桌会议投票：13/13 赞成
