## 1. 问题陈述

### 1.1 现状分析

灵笔 v0.5.0-dev 已完成大量功能代码，但存在以下结构性缺陷：

**领域模型瓶颈**
- 当前以 `Project` 为顶级实体，无法承载"一个世界观产出多部作品"的需求
- `CodexEntry` 泛化所有知识条目，角色/地点/传说/规则混杂在同一张表中
- 缺少 Volume → Chapter → Scene 的层级结构

**基础设施债务**
- 存储层使用 JSON 文件 + ZVec 向量库，缺少结构化查询能力
- 17 个 Service 直接依赖具体存储实现，难以单元测试
- 无数据迁移机制，版本升级困难

**AI 能力未与产品整合**
- 三层生成管线、质量审查、Prompt 工程已在 `lib/` 中实现，但无独立微服务承载
- 客户端直连 LLM Provider，缺少统一网关层（速率限制、熔断、成本监控）
- 项目上下文注入为硬编码，不可配置

**部署和社区空白**
- 无一键启动器，用户需手动启动 11 个微服务
- 无 Skill 生态系统，社区无法贡献扩展
- 商业化和配额系统未就绪

## 2. 目标

### 2.1 一句话目标

> 将灵笔从"Flutter 写作工具"升级为"AI 原生的世界写作平台"——一个统一的、可扩展的、可商业化的创作生态系统。

### 2.2 成功指标

| 指标 | 当前 | 目标 |
|------|:----:|:----:|
| AI 生成连贯章节成功率 | 未测量 | ≥80% |
| 从创意到第一章的时间 | 手动编写 | ≤5 分钟 |
| 角色一致性违规率 | 无检测 | ≤2 次/万字 |
| 微服务启动时间 | 无服务 | ≤30 秒 |
| 测试覆盖率（核心模块） | ~20% | ≥80% |
| 第三方 Skill 扩展 | 0 | ≥3 个社区 Skill |
| 首次启动到写作 | 配置复杂 | ≤2 分钟 |

### 3.2 领域模型层级

```
World (世界观容器)
 ├── Work (叙事作品，原 Project)
 │    ├── Volume (卷)
 │    │    ├── Chapter (章)
 │    │    │    └── Scene (场景)
 │    │    └── Document (文档)
 │    └── Timeline (时间线)
 ├── Canon (知识体系，原 Codex)
 │    ├── Character (角色)
 │    ├── Location (地点)
 │    ├── Lore (传说)
 │    └── WorldRule (世界规则)
 ├── CharacterGraph (关系图谱)
 ├── Faction (势力)
 ├── TimelineEvent (时间线事件)
 └── Foreshadowing (伏笔)
```

### 3.3 存储混合策略

| 数据类别 | 存储引擎 | 理由 |
|---------|---------|------|
| 结构化元数据 | Drift (SQLite) | 强类型、关系查询、迁移支持 |
| 正文内容 | 纯 .md 文件 | 不锁定数据、Git 友好 |
| 语义向量 | ZVec (本地) → Qdrant (远期) | 本地起步、远期可扩展 |
| 关系图谱 | 内存 + Drift → Neo4j (远期) | 当前数据量小 |
| 版本历史 | Git LFS + Drift 索引 | 成熟的版本控制 |
